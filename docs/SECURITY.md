# Security guide

## Required before internet exposure

- Terminate modern TLS at a trusted reverse proxy and enable secure cookies/HSTS.
- Replace the bootstrap password, create a least-privilege API key for each integration, and revoke
  unused sessions/keys. Never share one administrator key among customers.
- Keep `/etc/vexa-vm/vexa-vm.env` root-owned, group-readable only by the dedicated `vexa` service
  group (mode `0640`); back up the master key separately and test restoration.
- Bind QEMU VNC to loopback. Do not expose libvirt, QMP, VNC or the SQLite database to tenant networks.
- Restrict the service's libvirt/storage permissions and review systemd sandboxing after local network
  integration. The packaged unit bounds and exposes only `CAP_NET_ADMIN` for Vexa's checked
  nftables transaction; do not add `CAP_NET_RAW`, `CAP_SYS_ADMIN`, another ambient capability, or
  unrestricted passwordless sudo to the web process.
- Verify image SHA-256 values from an independent trusted source. Remote imports require that digest,
  use HTTPS port 443, pin public DNS answers, revalidate every redirect, stream at most 16 GiB into a
  temporary file, preserve a 512 MiB storage reserve, and publish only after a match. Keep node-level
  egress controls as defense in depth. On startup, the service removes only its own UUID-prefixed
  partial files that have been stale for at least 24 hours, so a concurrently active transfer is not
  mistaken for crash debris.
- Treat generated provisioning ISOs as credentials. With Guest Tools enabled, Vexa retires the exact
  media only after authenticated version-matched bootstrap. Tools-off Windows Cloudbase media has no
  trusted completion signal, may contain the initial password, and remains attached until an operator
  verifies first boot, rotates the password, and explicitly ejects/removes it. File unlinking does
  not guarantee forensic erasure on SSD or copy-on-write storage.
- Pin the official Ed25519 release public key outside panel-editable settings. A panel update must
  verify the detached signed manifest and artifact digest, show exact component/package changes, and
  obtain an explicit maintenance acknowledgement. The web process must never accept an arbitrary
  update URL, package name or host command. Treat
  `/run/vexa-vm/update-executor.ready` as available only when it is a root-owned safe regular file
  with the documented schema. Keep the update request/staging directories service-owned but their
  parent, processing, processed, rollback, receipt and status directories root-owned. See
  [Signed updates](UPDATES.md).

## Credentials and tokens

VM passwords use AES-256-GCM. Encryption is not a substitute for access control: only dedicated reveal
endpoints return a decrypted value, responses are not cacheable, and every reveal is audited without
the value. Rotating the master key should re-encrypt envelopes transactionally and retain a recoverable
old-key backup until verification completes.

API keys use a random prefix that supports identification plus a high-entropy secret. The database
stores only a SHA-256 digest and metadata. Customer and VNC URL credentials use the same hash-only
pattern. `GET /status/{token}` and `GET /vnc/{token}` exchange URL tokens server-side for a
short-lived `HttpOnly`, `SameSite=Strict` cookie and redirect to a token-free page. This removes the
secret from the address bar and subsequent browser history/referrers, but the original request path
can still enter reverse-proxy or access logs. Redact both token-path families in every logging layer.

An API key can carry an IPv4/IPv6 CIDR `ip_allowlist`. Treat it only as defense in depth. The source
address is the socket peer unless that peer is loopback; only a loopback peer may override it with
`X-Real-IP` or the first `X-Forwarded-For` value. The bundled deployment therefore requires the
reverse proxy to connect to Vexa-VM over `127.0.0.1` or `::1`. Forwarded address headers from any
non-loopback peer are ignored.

The VNC lifetime is exactly 600 seconds and cannot be refreshed by activity. On expiry the server
closes the WebSocket. A new link must be generated by an authorized admin/customer action.

## API controls

- Set the narrowest scopes (`vms:read`, `vms:write`, `network:read`, etc.) and an expiry.
- Send an `Idempotency-Key` for VM create/reinstall and retry only safe/idempotent requests.
- Enforce body/upload limits and application/reverse-proxy rate limits.
- Use an API-key IP allowlist only as defense in depth. Validate the loopback reverse-proxy path and
  the address it writes to `X-Real-IP`; there is no configurable non-loopback trusted-proxy range.
- Treat job errors as untrusted operational output. The public API returns a request ID instead of raw
  shell commands, stderr, filesystem paths or guest secrets.

## Reporting vulnerabilities

Do not open a public issue for a vulnerability. Send a minimal reproduction, affected version and
impact to the private security contact configured by the project maintainer. Avoid accessing data or
VMs that are not yours. Maintainers should acknowledge reports, publish patched releases and rotate
any exposed signing or infrastructure credentials.
